# Командная работа Career Quest

Команда состоит из двух участников. Единственный рабочий репозиторий — `BAITC-Hacks/hack-b18d812e-mcqueen`, созданный платформой HackAlem AI. Этот документ описывает фактическую работу, а не первоначальное предложение о разделении frontend/backend.

## Фактический вклад

| Участник | Выполненная работа |
| --- | --- |
| Напарник | Создал и загрузил базовое приложение, на котором продолжается работа команды. |
| Пользователь при помощи Codex | Проверил базовую реализацию; дополнил расчёты карьерной цели, обработку истории и импорт, проверки доступа и прогресса, тесты и документацию. Изменения интерфейса выполнялись по явной команде пользователя. |

Имена участников и авторство отдельных первоначальных файлов здесь не предполагаются. Вклад следует подтверждать фактическими изменениями и историей репозитория; коммиты от имени другого участника не создаются. Codex отправляет изменения только после явной команды пользователя.

## Текущая структура

- `server.js` — один HTTP-сервер Node.js: сессии, API, права доступа, локальное хранение и статические файлы.
- `lib/dataset.js` — загрузка и нормализация исходного набора, импорт дополнительных профилей.
- `lib/domain.js` — требования цели, допуски мероприятий, рекомендации, завершение и прогресс, HR-агрегаты.
- `lib/intelligence.js` — локальная статистическая модель завершения. Внешние AI API не подключены, ключи провайдера не требуются.
- `public/` — интерфейс сотрудника и HR на HTML/CSS/JavaScript.
- `tests/` — проверки доменной логики, выбора задач, практики, дальнейших целей, импорта и HTTP-сценариев.
- `docs/` и `README.md` — контракт, порядок запуска и результаты проверки.

Отдельные приложения в `backend/` и `frontend/` не создаются. Контракт существующего сервера описан в [api-contract.md](api-contract.md).

## Как продолжать без конфликтов

1. Перед этапом работы договориться, кто меняет конкретные файлы. Общий файл редактирует один участник за раз.
2. Сохранять существующую основу; изменения поведения сопровождать обновлением контракта и проверкой затронутого сценария.
3. Использовать ограниченные задачи: конкретный дефект или функция, проверяемый результат и краткий отчёт. Не переписывать готовые части без причины.
4. Перед объединением сверять изменения обоих участников. Публикацию выполняет один согласованный участник после команды пользователя.
5. Вместе проверять запуск и демонстрационный путь: вход → профиль → рекомендация → завершение → изменение навыков → HR → импорт профилей жюри.

Дальнейшие задачи назначаются по актуальному состоянию приложения, а не по прежнему жёсткому делению «один делает frontend, другой backend». Каждый участник должен понимать и уметь объяснить свой вклад.

## Проверка и данные

`npm start` запускает приложение, `npm test` выполняет тесты. Сведения о конкретном прогоне и его ограничениях фиксируются в [verification.md](verification.md); количество тестов само по себе не является гарантией выполнения всех требований кейса.

В репозиторий входит самостоятельно созданное синтетическое `demo.json`. Исходные наборы хакатона, рабочее состояние, личные пути и коды доступа остаются локальными. Для проверки используются каталог навыков, мероприятия, профили и история; внешней передачи данных моделью нет.

При проверке особое внимание уделяется обоснованию рекомендаций, карьерной цели и смене роли, критичным навыкам, ограничениям мероприятий, истории после последней оценки, защите от повторного начисления, импорту новых профилей и разделению доступа сотрудника/HR. Геймификация не относится к обязательному ядру текущей реализации.
